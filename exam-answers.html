Section 1 — APIs & Integrations

Q1. In simple terms, explain what an API is and what a webhook is. What is the difference between the two, and when would you use each one?

An API is like a menu at a restaurant — you send a request asking for something specific and you get a response back. You are the one initiating the call. For example, if I want to load a customer's profile, I call GET /customers/123 and the server sends me back the data. APIs are pull-based — you ask, you receive.

A webhook is the opposite — it's event-driven and push-based. Instead of my app asking "did anything change?", the other system calls my URL automatically when something happens. Like a doorbell — I don't keep going to the door to check; the bell rings when someone arrives.

I use APIs when I need to fetch or update data on demand — like loading a dashboard or submitting a form. I use webhooks when I need to react to an event in real time — like triggering an n8n workflow the moment a new lead is added in a CRM, without any polling. In my current work, most of my automation triggers are webhooks because they're instant and don't waste API quota checking for changes that may not have happened.

Q2. Imagine you need to connect two apps: when a new lead is added in a CRM, an automatic WhatsApp message should be sent to that lead. Walk me through, step by step, how you would build this. Mention the tools, the APIs, and the flow of data.

This is almost exactly a pattern I've built. Here's how I'd do it:

  1. CRM webhook setup: In the CRM (say HubSpot or Zoho), I'd configure a webhook that fires on "Contact Created". This sends a POST request with the lead's details — name, phone number, email — to a URL I control.
  2. n8n receives it: That URL is an n8n Cloud webhook trigger. n8n receives the payload and I add a Set node right after it to normalise the data — phone numbers often come in inconsistent formats, so I clean them to E.164 (+12125551234).
  3. Twilio sends WhatsApp: n8n then calls the Twilio API — POST to https://api.twilio.com/2010-04-01/Accounts/{SID}/Messages.json with To: whatsapp:+{phone}, From: whatsapp:+14155238886, and the message body.
  4. Update CRM: After sending, n8n calls the CRM's API to update the lead record — sets a "WhatsApp Sent" field to true with the timestamp, so the sales team can see it in the CRM.
  5. Error handling: If Twilio returns an error (invalid number, unverified recipient), n8n logs it to Supabase and optionally sends an alert to the team on Slack.

Tools: n8n Cloud (automation), Twilio (WhatsApp API), Supabase (logging), CRM native webhooks. I've built this exact pattern at Birbal AI for notification workflows — the logic is the same, just different services on each end.

Q3. What is the difference between a GET request and a POST request? Give a real example of when you would use each.

GET is for reading/fetching data. It doesn't change anything on the server. The parameters go in the URL. Example: when my React dashboard loads, it calls GET /appointments?date=2026-06-03 to retrieve today's appointments from Supabase. Refreshing the page calls the same endpoint safely — it only reads, never writes.

POST is for sending data — creating something new or triggering an action. The data goes in the request body, not the URL. Example: when a user submits the appointment form in my WhatsApp reminder app, the frontend calls POST /appointments with the customer name, phone, and time in the JSON body. This creates a new row in the database.

The simple rule I follow: if it's reading, use GET. If it's writing, creating, or triggering something, use POST (or PATCH for updates, DELETE for removal).

Q4. How do you keep API keys and secret credentials secure in a project? Name at least two specific methods.

  1. Environment variables + .gitignore: I never hardcode API keys in source code. All secrets go in a .env file which is added to .gitignore so it never gets committed to GitHub. In Vite/React projects I prefix frontend-safe values with VITE_ so only the values that must be on the client are exposed — server-side keys stay completely out of the bundle.
  2. n8n Credentials store: For all automation workflows, I use n8n's built-in encrypted credentials system. The Twilio Account SID, Auth Token, Supabase keys — all stored as named credentials in n8n, never visible in workflow JSON or execution logs. If someone reads the workflow code, they see credential: Twilio, not the actual key.
  3. Supabase Row Level Security: Even with a public anon key, I use RLS policies so the key can only perform the specific operations the app needs. Exposing an anon key without RLS would let anyone read or write your entire database.

Q5. You call an external API and it returns an error 429. What does that mean and how would you handle it in your code?

429 is "Too Many Requests" — the API is rate limiting me because I've sent too many calls in a short window. Every API has a limit (e.g. Twilio allows X messages per second on trial).

How I handle it:

  1. Check the Retry-After header in the response — the API usually tells you exactly how many seconds to wait before retrying.
  2. Implement exponential backoff — wait 1s, retry. If 429 again, wait 2s, retry. Then 4s, 8s. This prevents hammering the API repeatedly.
  3. In n8n, I use the Wait node to pause execution for the specified time before the next attempt.
  4. Long term, I'd also look at batching — instead of calling the API once per item, bundle multiple items into one call where the API supports it. And cache responses so I'm not re-fetching the same data repeatedly.

Q7. A business wants an automated agent that: (a) sends appointment reminders, (b) receives replies from customers, and (c) alerts a manager if a customer does not reply within 30 minutes. Explain how you would design this system. What handles the timing? Where is the data stored?

Sending reminders (a): A scheduled n8n workflow runs every 15 minutes. It queries Supabase for appointments in the next hour where reminder_sent = false. For each appointment, it fires a Twilio WhatsApp message and sets reminder_sent = true and reminder_sent_at = now().

Receiving replies (b): I configure a Twilio webhook URL that points to a second n8n workflow. When a customer replies on WhatsApp, Twilio POSTs to that URL with the sender's number and their message. n8n looks up the appointment by phone number, stores the reply text and replied_at timestamp in Supabase, and marks reply_received = true.

30-minute alert (c): Another scheduled n8n workflow runs every 5 minutes. It queries for rows where reminder_sent = true AND reply_received = false AND reminder_sent_at < now - 30 minutes AND alert_sent = false. For each match, it sends a Slack/email notification to the manager and marks alert_sent = true so the alert only fires once.

Data storage: Supabase (PostgreSQL) — one appointments table with columns: id, customer_name, phone_number, appointment_time, reminder_sent, reminder_sent_at, reply_received, replied_at, reply_text, alert_sent.

Timing is handled entirely by n8n's Schedule Trigger nodes — no external cron server needed.

Q8. What is the difference between sending a one-way notification message and building a two-way conversational bot? Which is harder and why?

One-way notification is fire-and-forget — trigger event, format message, send, done. It's stateless. You don't care what the customer replies.

Two-way conversational bot is significantly harder because:

  1. State management: You need to know where in the conversation each customer is. Did they just receive the first message? Did they reply "maybe"? Are they on step 2 of a 4-step confirmation? You need session state stored per-user, per-conversation.
  2. Unpredictable input: People don't reply the way you expect. They use abbreviations, different languages, typos, or completely off-topic messages. You need intent detection or at least simple NLP to classify their reply.
  3. Concurrency: Multiple customers can be at different stages simultaneously. The system needs to handle 100 open conversations without mixing up who said what.
  4. Timeouts and re-engagement: What if they don't reply? Do you follow up? After how long? How many times?

I've built one-way notifications reliably. Two-way bots I've designed architecturally — the core challenge is always the state machine and edge cases, not the messaging API itself.

Section 3 — AI Calling Agents

Q9. We want an AI agent that can make outbound phone calls to confirm appointments and understand the customer's spoken response. What tools or services would you use to build this? Name specific platforms (for voice, for speech-to-text, for the AI brain).

Here's the stack I'd use:

  • Voice / outbound calls: Twilio Voice or Vapi.ai. Vapi actually bundles most of the pipeline for you — it handles the call, STT, and TTS as one service and gives you a webhook to plug in your own AI. Twilio is more flexible but requires wiring each component yourself.
  • Speech-to-text (STT): Deepgram — it has the lowest latency of the options I've researched, handles real-world accents well, and has noise cancellation built in. Google Speech-to-Text is also solid if you're already in the Google ecosystem.
  • AI brain: Claude (Anthropic) or GPT-4. I'd send the transcribed text to the model with a system prompt that defines the agent's purpose — "you are a scheduling assistant confirming an appointment for {name} at {time}" — and let it decide the reply.
  • Text-to-speech (TTS): ElevenLabs for natural-sounding voice, or Google TTS if latency is the priority.

The overall flow: Twilio dials → Deepgram transcribes customer speech → Claude processes it → ElevenLabs converts Claude's reply to audio → Twilio plays it back. n8n can orchestrate the webhooks between these services and update the appointment status in Supabase based on the outcome.

Q10. An AI calling agent calls a customer, but the customer answers with background noise and an unclear response. How would you design the system to handle situations where the AI does not understand?

I'd design layered fallbacks:

  1. Noise filtering: Enable noise suppression in Deepgram — it filters out background audio before transcribing. Add a small silence buffer (300–500ms) after the customer stops speaking before sending to STT, so you don't cut them off mid-word.
  2. Confidence threshold: If Deepgram's confidence score on the transcript is below ~0.65, don't try to interpret it. Instead the agent says: "I'm sorry, I didn't catch that clearly. Could you repeat that?"
  3. Simplify after 2 retries: If after two attempts it still can't understand, the agent simplifies: "I just need a yes or no — can you say YES to confirm your appointment, or NO to cancel?"
  4. Hard fallback after 3 failures: The agent says "Let me connect you with our team" and either transfers to a live agent via Twilio call transfer or ends the call and triggers a follow-up SMS/WhatsApp asking them to reply by text.
  5. Log everything: All unclear responses get logged to Supabase with the raw audio/transcript for review — useful for improving the system over time.
Section 4 — Databases & Dashboards

Q11. You need to build a live dashboard that shows, in real time: today's appointments, which seller is assigned to each, and the status of each one. What database would you use, and how would you make the dashboard update in real time without the user refreshing the page?

I'd use Supabase (PostgreSQL) — and I've already done exactly this.

Supabase has a built-in Realtime feature powered by WebSockets. On the React frontend, you subscribe to a table channel and any INSERT, UPDATE, or DELETE on that table instantly pushes the change to every connected client without polling.

The setup in code is straightforward:

supabase.channel('appointments').on('postgres_changes', { event: '*', schema: 'public', table: 'appointments' }, callback).subscribe()

Whenever n8n updates an appointment status (e.g. marks confirmation_sent = true), the dashboard immediately reflects it — no refresh needed. I built this for the WhatsApp reminder project and the live update works reliably.

For the seller assignment, I'd add a seller_id foreign key on the appointments table joining to a sellers table. The dashboard query joins them: appointments?select=*,sellers(name)&appointment_date=eq.today.

Q12. Explain the difference between a SQL database (like PostgreSQL) and a NoSQL database (like Firebase). For a real-time operations dashboard, which would you choose and why?

SQL (PostgreSQL): Structured, relational, strict schema. You define tables, columns, and data types upfront. Rows in different tables are linked by foreign keys. Excellent for complex queries with JOINs — e.g. "give me all appointments today with the seller name and customer status". Data stays consistent because of constraints.

NoSQL (Firebase): Flexible, document-based, schema-free. You store JSON documents — good when your data shape changes frequently or you're prototyping fast. Firebase Realtime Database and Firestore both have real-time sync built in. But running relational queries ("give me all appointments for seller X that have status pending") is awkward — you denormalise and duplicate data instead of joining.

For a real-time operations dashboard I'd choose PostgreSQL via Supabase. Operations data is structured and relational — appointments have customers, sellers, statuses, timestamps. I need proper queries, filtering, and aggregations. Supabase gives me Postgres for the query power and Realtime for the live updates. Firebase would work for simple dashboards but becomes painful once the data model has any meaningful relationships.

Section 5 — GPS Tracking

Q13. We want to track field workers who distribute flyers, to know if they are moving or staying in one place too long. How would you capture their location? How would you detect if someone has not moved for, say, 30 minutes? What technology runs on the worker's phone?

Capturing location: On the worker's phone, a simple Progressive Web App (PWA) uses the browser's navigator.geolocation.watchPosition() API to capture GPS coordinates every 2–3 minutes. Each reading — { worker_id, lat, lng, accuracy, timestamp } — is sent to a Supabase worker_locations table via a POST request. If they have no data connection momentarily, the app queues the points and sends them when back online. No native app installation needed.

Detecting non-movement: An n8n scheduled workflow runs every 5 minutes. For each worker, it fetches their last 10 location records. Using the Haversine formula, it calculates the distance between the oldest and newest point in that window. If the total displacement is under ~50 metres AND the time span covers 30+ minutes, it flags the worker as stationary and sends an alert (WhatsApp/Slack) to the supervisor. After alerting, it marks the window as processed so the same period doesn't trigger a second alert.

Technology on the phone: A mobile-responsive PWA built in React — no app store required, works on any smartphone with GPS. GPS accuracy is typically 5–15m outdoors which is sufficient for this use case. I'd also add a battery-saving mode that reduces ping frequency if the worker has been moving continuously for a long time.

Q15. What is a 'prompt' when working with an AI model, and why does the way you write it matter? Give an example of a good prompt versus a bad prompt for a specific task.

A prompt is the instruction you send to the AI model — the text that defines what you want it to do, in what format, with what constraints. The model has no memory of your project or context unless you put it in the prompt, so the quality of your output is directly proportional to how clearly you specify the task.

Bad prompt: "Write a WhatsApp message about an appointment"

The AI doesn't know who the customer is, what the appointment is for, what tone to use, how long the message should be, or what to include. The output will be generic and probably unusable.

Good prompt: "You are a professional scheduling assistant for a water quality company. Write a WhatsApp confirmation message for a customer named {customer_name} whose appointment is on {date} at {time}. Keep it under 2 sentences. Be friendly and professional. Do not include marketing language or emojis. End with 'Reply STOP to unsubscribe.'"

The good prompt specifies: role (who the AI is), task (what to write), variables (what to substitute), constraints (length, tone, what to avoid), and required elements. The output is predictable, consistent, and immediately usable in the application.

Hardest part: State integrity across distributed workflows. A piece of content moves between states — draft → in review → revision requested → approved → published. Multiple n8n workflows could theoretically act on the same article simultaneously and create race conditions or double-notifications.

How I solved it: I made Supabase the single source of truth. Every workflow begins by reading the current status field and exits immediately if the status isn't what it expects. Updates happen atomically — read-check-update in a single database transaction. This prevented duplicate executions and made the whole pipeline auditable. Any engineer can look at the Supabase logs and see exactly what happened to every piece of content and when.

Q17. You are building a system and it is not working. The data is not arriving from one app to another. Walk me through your debugging process, step by step. How do you find where the problem is?

  1. Confirm the source is sending: I open Postman and manually send a request to the first endpoint — whether that's a webhook URL or an API. This tells me immediately whether the issue is in the sender or the receiver. If Postman gets the expected response, the source is fine.
  2. Check n8n execution logs: n8n shows exactly what data each node received and what it returned. I look for the first node where the output is empty, null, or shaped differently than expected. 90% of integration bugs are a data shape issue — the field is nested one level deeper than I thought.
  3. Inspect the payload in the browser: If the issue is on the frontend side, I open Chrome DevTools → Network tab and check the actual request being sent and the response coming back. This catches CORS errors, wrong URLs, or malformed JSON bodies.
  4. Test each service independently: If Supabase isn't updating, I test the query directly in Supabase's SQL editor. If Twilio isn't sending, I check their console error logs. Isolate each piece.
  5. Check credentials and environment: More times than I'd like to admit, the issue is an expired API key, the wrong .env variable loaded, or a production URL being called in a dev environment. I always verify these early now.
  6. Add temporary logging: If none of the above works, I add a Code node in n8n right after the suspicious point and log $json to trace what the data looks like at that exact moment.
